# Design tools (shared)

The developer chooses the tools per project during `bootstrap-product` (`design.lowFi`, `design.highFi`, `design.uiKit` in the config). Choosing a tool is not producing designs. Use exactly the configured tool; if it cannot do something the workflow needs, say so and ask — never switch tools silently.

## Fidelity rules

- **UI Kit first.** The shared visual foundation (tokens: color, type, spacing, radius, elevation; core components and states; patterns) is designed and approved before any feature design.
- **Low-fi for ALL MVP features in one `bootstrap-mvp` run.** Structure, hierarchy, flows and navigation — no visual polish.
- **Hi-fi per feature, later**, in `inspect-the-feature`: phone + tablet when the product targets them (and other relevant form factors), using the approved UI Kit. Reuse the approved, current low-fi instead of redoing it.
- Every approval records the exact artifact version (file commit/hash, Figma/Penpot version or page link) in the TM approval marker.

## The project's design playbook — `.leshi/design.md`

How THIS project uses its design tools lives in one short file, read **on demand** before any design work:

- **Connection block** (generated by `leshi sync`): which tool serves low-fi, hi-fi and the UI Kit, where each lives, and the capability table of each tool (verified / advertised / unavailable).
- **Below it** (owned by the project, started from the provider template in leshi-tools with `leshi design playbook`): file/page/board structure, naming, how designs are exported for review, how an approved version is pinned, the exact tool for each design operation, limitations and instance notes.

Rules:
1. Before creating, editing, exporting or reviewing designs, read `.leshi/design.md` and use the tools and locations it names.
2. Discovery: when a design tool is chosen (`bootstrap-product`, `bootstrap-existing-project`) or before relying on an operation the snapshot does not show as verified, list the tool's MCP tools (or, for HTML/tldraw, check the repo paths), exercise only read operations, and record the result: `leshi design record --provider <p> --via mcp|local --verified <ops> --advertised <ops> --unavailable <ops>`. `leshi design ops` prints the operations; `leshi design probe` does the same from the CLI when the server is reachable from it.
3. A tool without `design.create`/`design.update` is **review-only**: say so, and ask the developer whether to create the designs by hand in that tool or to use another authorized tool. Never switch tools silently.
4. If the playbook is missing or still has `_(fill)_` for an operation you need, run `leshi design playbook`, complete it from what discovery showed and get it approved (inside the project-setup gate during the bootstraps).
5. Keep it short: tables, ids, paths and exact tools — no design content.

## Visual quality bar

Professional, restrained, platform-native. No decorative "AI-style" gradients, glows, emoji or gratuitous animation. Accessibility: contrast, touch targets, dynamic type, focus order, motion that respects reduced-motion.

## Design craft

How leshi designs, whatever the tool. The approved visual direction of the product wins over any default here.

**Process**
- **Real products first.** Before designing a flow, study how strong products solve it (in and outside the category): what to adopt, what is table stakes, what they all do badly. Cite each reference.
- **Directions, then a choice.** For the visual direction, show 3–4 genuinely different directions side by side and let the developer choose; record what was rejected and why, in their words.
- **Every screen is specified:** the flow it belongs to, how it is presented (push, modal, sheet, overlay), what back does, its states (default, loading, empty, error, and the edge cases that matter), and the copy for states that are only text.
- **Defaults are visible.** Small decisions you take are listed as "defaults the developer can overrule", never buried.
- **Look at what you made.** Render or screenshot every board and check it before handing it over.
- **Approved designs keep a history:** a design changelog row (date, what, why) for every change to an approved artifact; the live file is the only truth; snapshot before a large revision.

**Principles**
- **Tokens only:** a spacing scale on a fixed base unit, a radius rule (e.g. one radius for actions, one for surfaces), semantic color roles in background/foreground pairs, one named type ramp. Each theme the UI Kit defines (e.g. light and dark) is designed, not inverted.
- **Hierarchy through restraint:** one accent; a color with meaning is never decoration; at most one primary action per screen; disabled reads quiet, not faded; elevation only where it separates layers.
- **Navigation has semantics:** pick push, modal, sheet or overlay by the job; flows that must not go back (completed payments, finished onboarding) remove back and draw their own exit; unsaved edits get a discard guard; exits land on a known screen.
- **Motion has a purpose** (feedback, orientation, continuity) and is short; entering eases out; every animation has a reduced-motion alternative; list what is deliberately not animated. Presses give immediate feedback.
- **Layouts respond to the window size class,** not to a device model; larger screens get a composition, not a stretched phone.
